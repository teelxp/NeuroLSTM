# Форматы данных

## 1. Газовая телеметрия CSV

Одна строка — одно наблюдение одного участка в один момент времени. Колонки:

| Колонка | Смысл и ограничения |
|---|---|
| `timestamp` | Временная метка; рекомендуемый вид `2024-01-01T12:00:00+03:00`. Переводится в UTC. Метка без часового пояса трактуется как UTC, поэтому часовой пояс необходимо указывать явно |
| `object_id` | Идентификатор участка. При отсутствии вся таблица считается одним объектом `single_object` |
| `pressure` | Измеренное давление. `pressure_unit`: `Pa`, `bar` или `MPa`; `pressure_reference`: `absolute` либо `gauge` |
| `temperature` | Температура газа, `C` или `K` в соответствии с `temperature_unit` |
| `flow_rate` | Самостоятельный измеренный расходный/режимный признак. Его единицы и смысл описываются в `data.provenance`; он не подменяет массовые расходы |
| `external_temp` | Внешняя температура в тех же единицах, что и `temperature` |
| `humidity` | Измеренная влажность; вид и единицы явно фиксируются в `humidity_description`. Относительная влажность не преобразуется в абсолютную автоматически |
| `mass_in`, `mass_out` | Измеренные массовые расходы на границах участка. `flow_unit`: `kg/s` либо `t/h` |
| `volume_m3` | Внутренний объем участка, м³, положительный; постоянен внутри одного объекта |
| `molar_mass_kg_mol` | Молярная масса газа, кг/моль, положительная; постоянна внутри одного объекта |
| `compressibility` | Коэффициент сжимаемости Z, положительный, может зависеть от времени |
| `accident` | Независимая метка наблюдаемого аварийного состояния 0/1; необходима для классификационной головы при `labels="column"` |

Колонки объема, молярной массы и Z можно не включать только тогда, когда соответствующие обоснованные константы явно заданы в `physics`. Для избыточного давления требуется `data.atmospheric_pressure_pa`; после его прибавления давление должно быть абсолютным и положительным. Внутри расчета используются Па, K, кг/с, м³, кг/моль и секунды.

Обязательные NaN/Inf, дубликаты и отсутствующие измерения приводят к понятной ошибке, а не к неявной интерполяции. Для разрывов требуется выделение непрерывных участков. Записи сортируются по объекту и времени. Изменение периода больше `period_tolerance` образует новый сегмент, и окно не пересекает такой разрыв. В разных объектах нельзя подменять один датчик другим продолжением общей последовательности.

### Цели и разбиение

Длина входа задается `window=L`; `horizons=[1,2,...]` — возрастающий список положительных целых горизонтов в шагах. Измеренные давление, расход и аварийная метка на строках `origin+h` становятся целями. Входные данные заканчиваются на `origin`. Для обратной разности dM/dt дополнительно нужен один предыдущий отсчет, поэтому фактически используется L+1 прошлых строк.

Границы train/validation/test едины по времени для всех объектов. Доли задаются по уникальным временным меткам, поэтому при неодинаковом покрытии объектов доли строк могут отличаться. Для каждого примера все входные строки, предыдущая строка производной и все целевые строки находятся в одной выборке. Число окон не совпадает с долей исходных строк; фактические числа отражаются в паспорте.

Нормировщик обучается только на train. Статистики test не используются для минимальных/максимальных значений. Постоянные входы отображаются в ноль. Постоянный целевой канал давления или расхода приводит к отказу: для такой задачи нужна отдельная постановка или явно заданный физический диапазон. Последний режим пока не реализован в данном CSV-конвейере.

### Тензор и потоки

`x` имеет форму `[B,L,3,3]`. Группа 0: давление, температура газа, `flow_rate`. Группа 1: внешняя температура, влажность, нулевое дополнение. Группа 2: входной и выходной массовые расходы, нулевое дополнение. Маска отличает заполненные позиции от дополнений.

В режиме `three_base_features` в W входят первые три числовых признака, в V — два контекстных, в M — отдельная нормированная оценка dM/dt по прошлым измерениям. Массовые расходы используются как физическая опора функционала. В режиме `seven_telemetry_features` в W дополнительно поступает полный семикомпонентный вектор; контекст V остается явным, как в записи (4.20). Это две разные конфигурации, не утверждение об одинаковом числе независимых входов.

### Средние расходы физического интервала

Для (4.10) используются средние **измеренные** расходы от момента выдачи прогноза до целевого момента. Значения средней величины получаются интегрированием по времени и делением на длительность интервала. Возможные правила: `trapezoid`, `left`, `right`; правило сохраняется в конфигурации. Средние, будущие T и Z используются только в loss и ретроспективной оценке. Они не передаются методу `AdaptiveLSTM.forward`.

Обучающая потеря проверяет связь давления с запасом газа. Она не заменяет измеренный `mass_out` прогнозом расходной головы и не сводит нестационарный баланс к `mass_in == mass_out`.

## 2. Семантический NPZ

Формат загружается с `allow_pickle=False`; массивы object/pickle недопустимы. N — число примеров, E — число событий на пример, D — размерность эмбеддинга, K — число смысловых компонент, r — размерность пространственной проекции. E фиксировано в одном файле; дополнение пустыми событиями без разметки не поддерживается.

| Массив | Форма / тип |
|---|---|
| `object_id` | `[N]`, строки NumPy Unicode, те же идентификаторы, что в CSV |
| `origin_time_ns` | `[N]`, int64: UTC Unix time в наносекундах |
| `available_time_ns` | `[N,E]`, int64: момент, когда входное событие уже было доступно; каждое значение не позже origin |
| `input_embeddings` | `[N,E,D]`, конечные вещественные значения входных событий |
| `reference_embeddings` | `[N,E,D]`, эталонные представления для обучения объяснительной компоненты; не подаются в декодер как вход |
| `basis_weight` | `[K,D]`, единая фиксированная матрица Wp для распределений по (3.88) |
| `basis_bias` | `[K]`, фиксированное смещение bp |
| `projection` | `[D,r]`, фиксированная Pr; требуется для причинной потери |
| `cause_pairs` | `[N,E,E]`, 0/1, только верхний треугольник j>i, без диагонали; внешняя разметка причинных пар |
| `coherent_pairs` | `[N,E,E]`, 0/1, без диагонали; внешняя разметка согласованных пар |
| `separate_pairs` | `[N,E,E]`, 0/1, без диагонали; разметка разделенных пар; не пересекается с coherent_pairs |
| `wave_index` | `[N,Nt,Nx]`, положительный показатель семантической среды; Nt,Nx >=3 |
| `wave_source` | `[N,Nt-2,Nx-2]`, комплексный или вещественный источник во внутренних узлах |
| `wave_intensity` | `[N,Nt,Nx]`, наблюдаемая/эталонная интенсивность смыслового поля |

Пары нужны только при включенных соответствующих потерях. В каждом примере активной парной потери должна быть непустая разметка. Семантический файл отбирает только те газовые окна, для которых существует точная пара `(object_id, origin_time_ns)`; итоговое количество окон фиксируется. Это нужно учитывать при сравнении режимов с семантикой и без нее.

Для включения задаются `semantics.path`, `embedding_size=D`, `state_components=K`, положительные веса выбранных потерь. `spatial_weights` содержит r положительных чисел. Для волновой потери дополнительно задаются размер шага `wave_dt`, `wave_dx`, скорость `wave_speed`, затухание `wave_damping` и вес интенсивности. Источник и интенсивность не вычисляются из одного лишь факта наличия текста.

Эмбеддинги, пары, базис и проекция должны быть подготовлены только с использованием допустимого обучающего корпуса/независимого предобучения, а не подстроены под будущую тестовую информацию. Проверка available_time_ns обнаруживает нарушенные временные метки, но не может доказать происхождение внешней модели эмбеддингов. Оно документируется пользователем отдельно.

Реализация SemanticHead — явно обозначенная инженерная параметризация: декодер строит предсказываемый эмбеддинг из скрытого состояния LSTM и входного эмбеддинга события. Дополнительная MSE-привязка `weights.reconstruction` не является отдельной формулой диссертации; ее можно отключить при обоснованном выборе остального функционала. Базис Wp не обучается совместно с этими потерями, чтобы не уменьшать KL простым вырождением общего базиса.

Семантический модуль не обращается к GPT, не генерирует свободный текст и не гарантирует истинность причинной интерпретации. Он предоставляет проверяемые математические операторы и обучение предсказываемых представлений при наличии источников и разметки. Модель `Emb` не выбрана за автора диссертации.

## 3. PINN NPZ

Для `TrainPINN.py` нужен отдельный пространственно-временной набор, а не номер строки CSV, объявленный координатой:

`x_m`, `t_s`, `pressure_pa`, `mass_flow_kg_s`, `accident`, `split`, `is_initial`, `is_boundary` — одномерные массивы `[N]`. Координата измеряется в метрах, время в секундах, давление в Па, расход в кг/с. `split=0/1/2` соответствует train/validation/test. `is_initial` и `is_boundary` — маски 0/1. Дополнительный `context` имеет форму `[N,Dcontext]`.

Максимальное время train меньше минимального validation, а максимальное validation меньше минимального test. Все выборки непустые. Начальные и граничные условия используются только из обучающего интервала. Нужны ненулевые обучающие диапазоны координат, времени, давления и расхода. Набор должен соответствовать одной согласованной физической задаче; объединение независимых сценариев требует корректного кодирования параметров в context.

```bash
python TrainPINN.py --config configs/pinn_local.json --output artifacts/pinn_run_01
```

Физические параметры `diameter_m`, `sound_speed_m_s`, `friction_lambda`, `baseline_velocity_m_s` задаются явно. Используется линеаризованная модель практически горизонтального участка при неотрицательной базовой скорости. Автоматически случайные положения датчиков и фиктивные граничные условия не создаются.

Координаты коллокации генерируются внутри диапазона обучения и сохраняются. Это расчетные точки, а не новые измерения. При наличии context он берется из train. Распределение условных параметров и координат — инженерный выбор этого baseline, не восстановленный протокол опубликованной апробации.

Для прямого сравнения с LSTM требуется подготовить общие целевые контрольные точки, горизонты, отложенные интервалы и определения метрик. Код отдельно вычисляет невязки PDE в их собственных единицах и не приравнивает их к проценту прошедших дискретный массовый баланс результатов.

## 4. Оценка согласованности и действия

`examples/decision_input.json` — иллюстративный пример отсутствующей семантической проверки, не данные реального решения. Команда:

```bash
python Neuro.py assess --input examples/decision_input.json --output artifacts/decision.json
```

Вход содержит три оценки `scores`, три показателя полноты `quality`, фиксированные положительные `omega`, пороги `thresholds` и независимую оценку uncertainty. Отсутствующее основание обозначается `null` с соответствующим q=0. Код не заменяет отсутствие информации нулевой ошибкой.

Функция `action_utility` вычисляет (4.56) по явно переданным эффектам действия. `rank_actions` получает уже рассчитанные полезности по сценариям и проверенные функции допустимости g<=0. По умолчанию обязательны группы `physical`, `technological`, `semantic`; внутри каждой группы необходимо учесть все обязательные ограничения предметного паспорта, например через их максимум. Для равенств используется величина вида `abs(residual)-tolerance`, а не сырая знакопеременная невязка. Даже диагностическое действие не считается допустимым без предусмотренных проверок.
